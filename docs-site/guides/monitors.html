Two check types

An http monitor calls your endpoint and judges the response. An ssl monitor watches the certificate and warns you before it expires.

Run from several regions

A monitor carries a list of regions. Each one gets its own schedule, its own result, and its own live chip in the app.

Failures become incidents

Consecutive failures past failure_threshold open an incident, notify your channels, and close again on recovery.

A monitor is one endpoint plus the rules for judging it: what to send, what counts as a good answer, how often to ask, and where to ask from. Everything on this page is also available over the REST API, so you can keep monitors in version control instead of clicking.

What a monitor holds

The request side is url, method, headers and body. Header values can be marked secret, in which case they are encrypted at rest and never come back in a read.

The judgement side is three independent assertions. A check passes only if all of the ones you set pass.

FieldWhat it asserts
expected_status_codesThe response status is in this set. Takes single codes and ranges, for example 200,201,300-399.
max_latency_msThe response arrived within this many milliseconds. Leave it null to ignore latency.
body_containsThe response body contains this substring. Leave it null to ignore the body.

timeout_seconds is separate from max_latency_ms. The timeout gives up on the request; the latency assertion fails a response that did arrive, just too slowly.

How often it runs

interval_seconds is what you ask for. Your plan sets a floor, so the cadence the scheduler actually uses is the slower of the two. The monitor list returns that effective value in interval_seconds and the next due time in next_check_at, so the app can say "checks every N" honestly rather than repeating what you typed.

Check now is rate limited. The manual check-now button and its API route run one check immediately, outside the schedule. It is limited per monitor, so it cannot be used to get a faster cadence than the plan allows.

Several regions

Add a region to regions and the scheduler starts dispatching that region's jobs straight away, with no redeploy. Each region reports its own result and keeps its own live state, so you can see that a monitor is fine from one place and failing from another.

down_policy is how those per-region verdicts combine into one. Today each region's result stands on its own; the cross-region reduce is not wired yet.

From failure to incident

  1. A check fails. One failure is not an incident, it is a data point.
  2. Failures in a row reach failure_threshold. The monitor is now down.
  3. An incident opens and every channel in notification_channel_ids is notified once.
  4. A later check passes. The incident closes, and a recovery notification goes out.

An incident carries the timeline of what happened. You can annotate it while it is open, and an admin can close one by hand as an operator override when the automatic close is not appropriate.

Creating one from the API

curl -X POST https://api.pulsepager.com/api/v1/orgs/<orgId>/monitors \
  -H "Authorization: Bearer pulse_sk_your_secret_here" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "http",
    "name": "api health",
    "url": "https://api.example.com/health",
    "method": "GET",
    "expected_status_codes": "200",
    "max_latency_ms": 800,
    "interval_seconds": 60,
    "failure_threshold": 2,
    "regions": ["eu-central", "us-west"]
  }'

A monitor starts enabled. Set enabled to false to pause it without losing its history or its settings.

Certificate monitors

An ssl monitor checks the certificate on the host in url and reports its expiry. The point is lead time: you hear about a certificate weeks before it lapses, rather than when the first customer does.

Keys and roles are covered in Authentication. Every field and route is in the API reference.
